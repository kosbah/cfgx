All phases are built. They were implemented in the order 1, 2, 5, 3, 4, 6, 7, 8 (Phase 0 was
the initial repository skeleton; its CI and lint setup were fixed in Phase 8). Each phase
is one stacked pull request against `epistemer/cfgx:master`.

The sections below are the original plan. Where the built code differs, the code, the
[README](README.md) and [docs/design](docs/design) are authoritative; the notable
differences are listed under each phase as **As built**.

## Phase 1 — Core DSL (`cfgx` package)

**Goal:** Implement the developer-facing DSL. This is the only package that application
developers import in their schema files. It must be polished, ergonomic, and well-documented.

**Outputs:**
- `cfgx.go` — `Define()`, package-level doc
- `schema.go` — `Schema` type, `MutuallyExclusive()` constraint
- `entry.go` — all entry constructor functions and builder chain
- `internal/ir/schema_ir.go` — `SchemaIR`, `EntryIR`, `ConstraintIR` types and JSON marshaling
- Unit tests for all builder methods
- Tests for `SchemaIR` round-trip serialization (marshal → unmarshal → equal)

**Key design constraints:**
- Use generics (`T comparable`) for `Default(val T)` and `Validate(fn func(T) error)`
- The `Schema` value must be retained at runtime (the runtime package uses it for
  validators and IsLive watching)
- Closures (`OnChange`, `Validate`, `Getter`) are stored in the Schema at runtime but
  are NOT serialized into `SchemaIR`; they are flagged as `HasOnChange: true` etc.
- All builder methods return the entry receiver for chaining
- No external dependencies except the standard library

**See:** [docs/design/config-anatomy.md](docs/design/config-anatomy.md),
[docs/design/schema-ir-spec.md](docs/design/schema-ir-spec.md),
[docs/agents/phase1-dsl.prompt.md](docs/agents/phase1-dsl.prompt.md)

## Phase 2 — Schema parser (`gen/parser`)

**Goal:** Given a Go source file containing a `cfgx.Define(...)` call, parse it statically
using `go/ast` and return a `SchemaIR`.

**Outputs:**
- `gen/parser/parser.go` — `Parse(filename string) (*ir.SchemaIR, error)`
- `gen/parser/parser_test.go` — table-driven tests against `testdata/schemas/` fixtures
- Error types with file/line information

**Key design constraints:**
- Use only `go/parser` and `go/ast` from the standard library; no CGo, no external tools
- Extract only statically knowable values (string/int/bool/float literals)
- Closures (function literals) must be detected and noted (`HasOnChange: true`) but not extracted
- Must handle nested `cfgx.Object()` recursively
- Must handle `cfgx.MutuallyExclusive()` constraints
- Return a structured `ParseError` (not a plain string) with `File`, `Line`, `Column`, `Message`

**See:** [docs/agents/phase2-parser.prompt.md](docs/agents/phase2-parser.prompt.md)

## Phase 3 — Go code generator (`gen/codegen`)

**Goal:** Given a `SchemaIR`, emit a complete, formatted Go source file.

**Outputs:**
- `gen/codegen/codegen.go` — `Generate(schema *ir.SchemaIR, pkg string) ([]byte, error)`
- `gen/codegen/templates/config.go.tmpl` — the Go template
- `gen/codegen/codegen_test.go` — golden-file tests (input IR → expected .go output)
- `testdata/golden/` — golden `.go` files

**Generated file contract** (what `config.gen.go` must contain):
- `// Code generated by cfgx. DO NOT EDIT.` header
- One root `Config` struct with a field per top-level entry
- One nested `XxxConfig` struct per `Object` entry
- Getter methods on all structs (value type for primitives, pointer for optional objects)
- Sensitive fields: `string` internally; `String()` returns `"[redacted]"`; excluded from `%v`
- Computed fields: stored as a `func() T` closure; exposed as a method
- `RegisterFlags(cmd *cobra.Command, schema *cfgx.Schema)` — registers cobra flags with
  descriptions and defaults from the Schema
- `BindViper(v *viper.Viper, schema *cfgx.Schema)` — binds all env names
- `Load(schema *cfgx.Schema, v *viper.Viper) (*Config, error)` — reads viper, populates
  structs, calls `schema.Validate()` for runtime validators; returns a multi-error

**Key design constraints:**
- Use `text/template`; call `go/format.Source()` on output before returning
- Never use `fmt.Sprintf` to build Go source directly
- Scoped entries only appear in the struct generated for that scope (not in root Config)

**See:** [docs/agents/phase3-codegen.prompt.md](docs/agents/phase3-codegen.prompt.md)

**As built:**
- `Generate(schema *ir.SchemaIR, opts codegen.Options)`; `Options` carries the package name,
  the cfgx module path and the source file shown in the header.
- `BindViper(v *viper.Viper, schema *cfgx.Schema)`: flags registered by `RegisterFlags` are
  bound from there, so `BindViper` needs no command argument.
- Besides `Load` (shared `Config`), one `Load<Scope>` per scope returns a `<Scope>Config`
  that embeds `Config`. Each validates with `schema.ValidateScope(v, scope)` and returns a
  `*cfgx.ValidationErrors`.
- Getters everywhere (`cfg.Port()`, `cfg.Db().Host()`); a Sensitive getter returns the plain
  `string`, while the stored value redacts itself when printed or marshalled.
- The generated file imports `github.com/epistemer/cfgx` (for `*cfgx.Schema`) as well as
  `cfgx/runtime`, cobra and viper. When the schema has IsLive entries, Load starts a
  `runtime.Watcher` and the config gets a `Close` method.

## Phase 4 — Artifact generators (`gen/artifacts`)

**Goal:** Given a `SchemaIR`, emit all non-Go artifacts.

**Outputs:**
- `gen/artifacts/env.go` — `.env.example` generator
- `gen/artifacts/yaml.go` — `config.example.yaml` generator
- `gen/artifacts/jsonschema.go` — JSON Schema (draft-07) generator
- `gen/artifacts/markdown.go` — `docs/config.md` generator
- `gen/artifacts/manpage.go` — `docs/config.1` (groff) generator
- `gen/artifacts/artifacts_test.go` — golden-file tests for each generator

**Key design constraints:**
- Sensitive entries: in `.env.example` and `config.example.yaml`, write empty string with
  `# REQUIRED — sensitive, do not commit` comment
- Deprecated entries: strike-through in markdown; `## DEPRECATED` annotation in env/yaml
- Nested objects: YAML uses block structure; `.env` flattens with `DB_HOST` naming
- JSON Schema: map Go types → JSON Schema types; `"writeOnly": true` for sensitive

**See:** [docs/agents/phase4-artifacts.prompt.md](docs/agents/phase4-artifacts.prompt.md)

## Phase 5 — Runtime package (`cfgx/runtime`)

**Goal:** Provide the thin runtime helpers that the generated code imports. Must add
minimal startup overhead.

**Outputs:**
- `runtime/validator.go` — `Registry`, `Register()`, `Get()`, `ValidateAll()`
- `runtime/validators.go` — built-in validator constructors (see list below)
- `runtime/watcher.go` — `Watcher` struct for IsLive polling/watching
- `runtime/runtime_test.go` — unit tests and a watcher benchmark

**Built-in validators:**

| Name | Function signature | Notes |
|------|-------------------|-------|
| `Email()` | `func(string) error` | RFC 5322 |
| `URL()` | `func(string) error` | must parse with `url.Parse` |
| `Port()` | `func(int) error` | 1–65535 |
| `PortRange(min, max int)` | `func(int) error` | custom range |
| `Base64()` | `func(string) error` | standard or URL-safe encoding |
| `Regex(pattern string)` | `func(string) error` | compile at construction; match at call |
| `Duration()` | `func(string) error` | parseable by `time.ParseDuration` |
| `Semver()` | `func(string) error` | vX.Y.Z format |
| `Enum(values ...string)` | `func(string) error` | case-insensitive |
| `Range(min, max float64)` | `func(float64) error` | inclusive |

**Watcher contract:**
- `NewWatcher(interval time.Duration) *Watcher`
- `Register(envName string, getter func() (any, error), ptr any, onChange func(old, any))` 
- `Start(ctx context.Context)` — launches background goroutine
- `Stop()` — cancels context, waits for goroutine to exit
- For file-backed configs: uses `github.com/fsnotify/fsnotify`
- IsLive env vars: polled every `interval` using `os.Getenv`; compared with stored value

**Key design constraints:**
- Zero allocations per watcher tick when no changes occur
- Atomic stores for IsLive value pointers (use `sync/atomic` or `sync.RWMutex`)
- The Watcher goroutine must respect context cancellation within one tick

**See:** [docs/agents/phase5-runtime.prompt.md](docs/agents/phase5-runtime.prompt.md)

**As built:** `Watcher.Register` takes a `runtime.WatchEntry` struct (Key, Env, ConfigFile,
Getter, ValuePtr `*atomic.Value`, OnChange) and `SetReloader` sets the function run on a
config file change. The built-in validators live once in `internal/validate` and are wrapped
by both the root package (typed, for the DSL) and `runtime` (`ValidatorFunc`, for the
registry). `runtime.ValidateSchema` validates a `SchemaIR` statically for `cfgx validate`.

## Phase 6 — CLI tool (`cmd/cfgx`)

**Goal:** Implement the `cfgx` binary. Use cobra for the CLI itself.

**Outputs:**
- `cmd/cfgx/main.go`
- `cmd/cfgx/cmd_init.go` — `cfgx init [module-path]`
- `cmd/cfgx/cmd_gen.go` — `cfgx gen`
- `cmd/cfgx/cmd_validate.go` — `cfgx validate`
- `cmd/cfgx/cmd_docs.go` — `cfgx docs`
- `cmd/cfgx/templates/` — embedded scaffold templates for `cfgx init`
- `cmd/cfgx/cmd_*_test.go` — integration tests per command

**Command specifications:**

### `cfgx init [module-path]`
- Creates: `go.mod`, `main.go`, `cmd/root.go`, `cmd/serve.go`, `cmd/schema.go`
- `cmd/schema.go` contains a working example schema with port, debug, and a db object
- Runs `go mod tidy` after scaffolding (or prints a reminder if not available)
- Idempotent: refuses to overwrite existing files unless `--force`

### `cfgx gen [-schema ./cmd/schema.go] [-out-dir .] [-pkg cmd]`
- Calls `gen/parser.Parse(schemaFile)`
- Calls `gen/codegen.Generate(ir, pkg)` → writes `<out-dir>/<pkg>/config.gen.go`
- Calls each artifact generator → writes to `<out-dir>`
- Prints a summary: `✓ wrote cmd/config.gen.go`, `✓ wrote .env.example`, etc.

### `cfgx validate [-config ./config.yaml] [-env] [-schema ./cmd/schema.go]`
- Parses schema, builds a viper instance from the config file and/or env
- Runs `Load()` to trigger all validators
- Prints each error with field path and message
- Exits 0 on success, 1 on validation failures, 2 on tool errors

### `cfgx docs [-format md|man|json-schema] [-out ./docs] [-schema ./cmd/schema.go]`
- Runs only the requested artifact generator(s)

**See:** [docs/agents/phase6-cli.prompt.md](docs/agents/phase6-cli.prompt.md)

**As built:** templates live in `cmd/cfgx/scaffold/templates/` and `cfgx init` also writes
`cmd/migrate.go`, then runs `cfgx gen` and `go mod tidy`. `cfgx gen` writes `config.gen.go`
next to the schema and the artifacts to `--out-dir` (default: the module root). `gen`,
`validate` and `docs` auto-discover a single `schema.go` when `--schema` is omitted.
`cfgx validate` uses `runtime.ValidateSchema` rather than a generated `Load()`, so it can't
run custom `Validate` closures or Getters, and it isn't scope-aware.

## Phase 7 — Integration & examples

**Goal:** Verify the entire pipeline works end-to-end with a realistic project.

**Outputs:**
- `examples/webapp/` — a realistic app with a `serve` and `migrate` command
- `examples/webapp/cmd/schema.go` — uses most cfgx features
- `examples/webapp/pkg/server/` and `pkg/database/` — define their own interfaces
- `examples/webapp/README.md` — explains how to run the example
- `_test/e2e/` — end-to-end tests:
  1. `cfgx gen` on the example schema produces valid, compilable Go
  2. `cfgx validate` accepts a valid config and rejects an invalid one
  3. The generated `Load()` correctly populates all fields
  4. The `Watcher` detects an env var change within two poll intervals
- Benchmark: compare startup time (schema parse + Load) against a baseline hand-written viper project

**Success criteria:**
- `cd examples/webapp && go build ./...` succeeds using only the generated files
- All e2e tests pass
- Benchmark shows ≤ 2× startup overhead vs. bare viper

**As built:** all criteria met except the benchmark. `LoadServe` costs about 3.9× plain viper
reads (about 6× on a 4-core Linux VM) because it also validates every value and starts the
IsLive watcher. The e2e tests live in `_test/e2e/` (build tag `e2e`) and
`examples/webapp/cmd/*_e2e_test.go`.

## Future considerations (post-v1)

- `cfgx init` project template presets: `web`, `worker`, `cli-tool`
- SIGHUP reload support in the Watcher
- Auto-detection of config file format (YAML, TOML, JSON) via viper
- VS Code extension for schema file editing with autocompletion
- Config diffing output: `cfgx validate --diff` shows what changed between two configs
- Plugin validator system (`cfgx.RegisterValidator("my-validator", fn)` in init())
